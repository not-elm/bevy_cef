# Bevy 0.20 Migration — Design

Date: 2026-10-14
Status: Approved (design sections §1–§4 approved in brainstorming; plan cross-checked by a parallel Codex + Claude research pass against the unpacked Bevy 0.20 sources)
Target version: 0.14.0 (breaking)

## Goal

Make bevy_cef build and behave correctly on Bevy 0.20.0 (released 2026-10-08, wgpu 30), and
release it as 0.14.0. CEF stays pinned at `152.3.0+152.0.6`.

"Behave correctly" is the hard part. Bevy 0.20 contains several changes that compile cleanly
but silently break bevy_cef at runtime — the same class of problem as the 0.19 `AssetMut`
change that turned webviews black without a compile error. This design names each of them
and the fix.

## Background

### What Bevy 0.20 changes for bevy_cef

Compile-time breaks (the compiler finds these):

- **wgpu 29 → 30.** `bevy_render 0.20` depends on `wgpu ^30`. In wgpu-hal 30,
  `metal::Device::texture_from_raw` gains a `drop_callback: Option<DropCallback>` parameter
  (`wgpu-hal-30.0.1/src/metal/device.rs:415`), and `wgpu::Device::create_texture_from_hal`
  gains `initial_state: wgt::TextureUses` (`wgpu-30.0.1/src/api/device.rs:320-345`).
  Both are called from `crates/bevy_cef_core/src/browser_process/accelerated_paint/iosurface.rs`.
- **Flat pointer events.** `Pointer<Press>` becomes `PointerPress` (fields stored directly
  on the event; `Pointer` is now a non-generic `pointer` field), and generic code uses the new
  `PointerEvent: EntityEvent` trait (`bevy_picking-0.20.0/src/events.rs:74-130, 312-327`).
  19 sites across `src/drag.rs`, `src/focus.rs`, `src/webview/mesh.rs`,
  `src/webview/webview_sprite.rs`, `src/webview/ui/input.rs`, `src/resize/plugin.rs` and
  `src/system_param/pointer.rs`.
- **Other API changes** surfaced by the compiler (observer event generics, extraction moved
  to `bevy_extract`, `ComponentId`/`Name` conversions, etc.). They are fixed mechanically.

Runtime-only breaks (the compiler does NOT find these):

- **naga_oil removed; shaders are WESL.** `#define_import_path` / `#import` no longer
  exist. `Shader::from_wgsl` records no imports (`bevy_shader-0.20.0/src/shader.rs:135-147`),
  so an unmigrated shader compiles fine in Rust and fails only when the pipeline is built.
  bevy_cef has five such shaders: `src/webview/mesh/webview_util.wgsl`,
  `src/webview/mesh/webview_extend_standard_material.wgsl`, `src/webview/ui/webview_ui.wgsl`,
  `assets/shaders/custom_material.wgsl`, `assets/shaders/headless_texture.wgsl`. In addition,
  `bevy_pbr::pbr_functions::alpha_discard` now takes three arguments
  (`bevy_pbr-0.20.0/src/render/pbr_functions.wesl:98`); the standard-material shader calls the
  two-argument form.
- **`Sprite` renders through `Mesh2d` + `Material2d`.** On `Added<Sprite>`, Bevy inserts
  `Mesh2d(quad)` and then `MeshMaterial2d<SpriteMeshMaterial>` in `PostUpdate`
  (`bevy_sprite_render-0.20.0/src/sprite_mesh/mod.rs:47-80, 176-206`). `Mesh2d` is not a
  required component (`bevy_sprite-0.20.0/src/sprite.rs:15`). Two consequences — see
  "Sprite webviews" below.
- **`RenderGraph` system sets are weakly chained** (`bevy_render-0.20.0/src/renderer/mod.rs:50-61`).
  This does not break bevy_cef (see "Render graph ordering"), but it falsifies an existing
  code comment.
- **UI rendering is retained.** This does not break bevy_cef (see "UI materials").

### MSRV

`bevy 0.20.0` declares `rust-version = "1.97.1"` (`bevy-0.20.0/Cargo.toml:14`), and
`wgsl-types 0.6` (pulled in by Bevy's WESL stack) requires the same. A 1.96 toolchain fails
dependency resolution with an error that names `wgsl-types`, not Bevy.

### Why CEF is not touched

The original plan also bumped CEF to 154. Research found that `cef 154.5.0` no longer
contains `register_extension` (CEF marks `CefRegisterExtension` `removed=15400` in
`include/cef_v8.h` on branch 8037), which bevy_cef uses to install `window.cef`
(emit/listen/brp) and `CefExtensions`. CEF's branch table also lists 154 (8037) as a Legacy,
unsupported branch. Bumping CEF therefore means rewriting the JS bridge, and it is split out
into a separate future project (JS bridge rewrite + CEF 156).

`Cargo.toml` declares `cef = "152.3.0+152.0.6"`, which is a caret requirement: an
unrestricted `cargo update` resolves it to `152.4.0+152.0.8`. Lockfile updates in this work
are therefore targeted at the Bevy/wgpu packages only.

## Requirements

1. The workspace depends on `bevy 0.20`, `bevy_remote 0.20`, and `wgpu 30`; `cef` and
   `cef-dll-sys` resolve to `152.3.0+152.0.6` in `Cargo.lock`.
2. The workspace declares `rust-version = "1.97.1"` and every member inherits it.
3. All five shaders are WESL and load without shader-compilation errors at runtime.
4. A user custom-material shader can import the webview sampling helper as
   `import bevy_cef::webview::util::surface_color;`.
5. A sprite webview receives each pointer and wheel event exactly once, through the sprite
   input path only.
6. A sprite webview shows the live page from its first painted frame and after every resize,
   on both the macOS GPU path and the Windows/Linux CPU path.
7. Mesh, UI, and headless-target webviews keep their current rendering and rebind behavior.
8. Static checks pass with zero warnings: `cargo check --workspace --all-targets`,
   `cargo clippy --workspace --all-targets --all-features -- -Dwarnings`, `cargo fmt --check`,
   `cargo test --workspace --no-default-features --tests`, `cargo test --doc`.
9. `cargo check -p bevy_cef_core --no-default-features` (the render-process build) still pulls
   no wgpu / Metal stack.
10. Every commit on the branch builds, renders, and accepts input correctly (C1 on Bevy 0.19,
    C2 and C3 on Bevy 0.20).

## Design Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | CEF is not changed in this release | `register_extension` removal makes any CEF ≥ 154 a JS-bridge rewrite; 154 is already Legacy. |
| D2 | One PR, three commits (C1 prep on 0.19, C2 migration, C3 docs) | Each commit builds and works; the sprite filter fix lands before the bump as a no-op. |
| D3 | Sprite webviews keep using `Sprite` | Replacing it with a bevy_cef-owned `Mesh2d` + `Material2d` would break the `Sprite` API (`examples/sprite.rs`, resize sprite branch, `obtain_relative_pos`) and lose sprite picking's alpha test. Deferred. |
| D4 | Sprite rebind touches the `SpriteMeshMaterial`, replacing the `Image` touch | In 0.20 a Material2d is re-prepared only on its own asset events; touching the image has no remaining consumer for sprites. |
| D5 | The CPU path touches the sprite material on every paint | `MeshMaterial2d<M>` preparation has no ordering dependency on `GpuImage` (`bevy_sprite_render-0.20.0/src/mesh2d/material.rs:342`), so a one-shot touch on the reallocation frame can capture the old view. The mesh and UI CPU paths already touch their material on every paint. |
| D6 | The shared shader helper moves to `src/webview/util.wesl` and is registered with `load_shader_library!` | The embedded path `embedded://bevy_cef/webview/util.wesl` becomes the stable module path `bevy_cef::webview::util` (`bevy_shader-0.20.0/src/shader.rs:176-200`), close to the old `webview::util`. Keeping the old location would expose `bevy_cef::webview::mesh::webview_util`. |
| D7 | Internal shaders use `embedded_asset!` + `ShaderRef::Path("embedded://bevy_cef/…")`, not `load_internal_asset!` | `load_internal_asset!` derives the module path from the source-file path relative to `file!()` (`bevy_asset-0.20.0/src/io/embedded/mod.rs:388-400`). |
| D8 | `webview_blit` gets an explicit `.before(RenderGraphSystems::Render)` | Not required (see below), but the existing comment claims a strict chain that no longer exists. |
| D9 | `WebviewPointer` keeps its method names and becomes generic over `E: PointerEvent` | It is crate-internal (`mod system_param;` is private and not in the prelude); call sites infer the type and need no change. |
| D10 | `docs/website/` is not updated | Same as the 0.19 migration; the site is already stale and refreshing it is a separate task. |

## Commit Structure

**C1 — prep on Bevy 0.19 (no behavior change).**
Introduce a crate-internal filter alias for mesh-path webviews and use it at all four sites:

```rust
pub(crate) type MeshWebviewFilter = (Or<(With<Mesh3d>, With<Mesh2d>)>, Without<Sprite>);
```

Sites: `src/webview/mesh.rs` (`setup_observers`, `on_mouse_wheel`), `src/drag.rs`
(~L215), `src/resize/plugin.rs` (~L49). On 0.19 sprite webviews never carry `Mesh2d`, so
this is a no-op. Add the regression test (see Verification).

**C2 — Bevy 0.20 / bevy_remote 0.20 / wgpu 30.**
Dependency bump, MSRV, all compile fixes, the WESL migration, the IOSurface import update,
and the sprite rebind fix. After C2 everything renders and accepts input correctly.

**C3 — docs and release.**
Version 0.14.0, README / CLAUDE.md / CHANGELOG.

## Architecture

### Dependencies and MSRV (C2)

- Root `Cargo.toml`: `bevy = { version = "0.20", default-features = false }`,
  `bevy_remote = "0.20"`. `crates/bevy_cef_core/Cargo.toml`: `wgpu = { version = "30", … }`.
- Lockfile: `cargo update -p bevy -p bevy_remote -p wgpu` (plus any package cargo names as a
  conflict). Never a bare `cargo update`. Confirm afterwards that `Cargo.lock` still pins
  `cef` and `cef-dll-sys` at `152.3.0+152.0.6`.
- `[workspace.package]` gains `rust-version = "1.97.1"`; every member `Cargo.toml` (root,
  `bevy_cef_core`, `bevy_cef_render_process`, `bevy_cef_debug_render_process`,
  `bevy_cef_bundle_app`) gains `rust-version.workspace = true`.
- Feature names are re-checked against Bevy 0.20 (`bevy_ui_render`, `bevy_sprite`,
  `picking`, `x11`, `wayland`, …); the compiler reports renames.

### Pointer events (C2, crate-internal)

- Observers take the flat events: `On<PointerMove>`, `On<PointerPress>`,
  `On<PointerRelease>`, `On<PointerScroll>`.
- `WebviewPointer::pos_from_trigger` / `pos_from_trigger_raw` become
  `fn pos_from_trigger<E: PointerEvent>(&self, trigger: &On<E>) -> Option<(Entity, Vec2)>`
  (and the `_raw` equivalent). The target entity comes from `event_target()` and the
  viewport position from `pointer().position`.
- `obtain_relative_pos_from_trigger` in `webview_sprite.rs` gets the same shape.
- `PointerPress.count` is not forwarded to CEF (out of scope; click count stays 1).

### Shaders (C2)

| Shader | New file | Registration | Referenced as |
|---|---|---|---|
| webview sampling helper | `src/webview/util.wesl` | `load_shader_library!` in the plugin defined in `src/webview.rs` | module `bevy_cef::webview::util` |
| standard material | `src/webview/mesh/webview_extend_standard_material.wesl` | `embedded_asset!` | `ShaderRef::Path("embedded://bevy_cef/webview/mesh/webview_extend_standard_material.wesl")` |
| UI material | `src/webview/ui/webview_ui.wesl` | `embedded_asset!` | `ShaderRef::Path("embedded://bevy_cef/webview/ui/webview_ui.wesl")` |
| example custom material | `assets/shaders/custom_material.wesl` | asset | `"shaders/custom_material.wesl"` |
| example headless target | `assets/shaders/headless_texture.wesl` | asset | `"shaders/headless_texture.wesl"` |

- WESL syntax: `import a::b::{c, d};` at the top; `@group(#{MATERIAL_BIND_GROUP})` becomes
  `@group(constants::MATERIAL_BIND_GROUP)`; Bevy module paths follow crate file paths
  (e.g. `bevy_ui::ui_vertex_output` → `bevy_ui_render::ui_vertex_output`,
  `bevy_pbr::forward_io` → `bevy_pbr::render::forward_io`). Exact paths are taken from the
  0.20 sources.
- `surface_color(uv)` keeps its signature and bindings 101/102.
- The `alpha_discard` call is updated to the three-argument form.
- The `uuid_handle!` constants and `load_internal_asset!` calls for these shaders are removed.

### macOS IOSurface import (C2)

- `texture_from_raw(…, drop_callback: None)`: the `RetainedIoSurface` + `MTLTexture`
  ownership already keeps the surface alive, so no callback is needed.
- `create_texture_from_hal(hal_tex, &desc, wgpu::TextureUses::RESOURCE)`. The IOSurface
  holds pixels CEF already painted, so `UNINITIALIZED` is wrong (wgpu may treat the contents
  as discardable). `RESOURCE` matches the state cef-rs's own IOSurface importer passes
  (`cef-152.4.0+152.0.8/src/osr_texture_import/iosurface.rs:171-174`). Metal has no layout
  transitions, so this choice affects only wgpu's initialization tracking.
- The module doc comment's "for wgpu 29" is updated.

### Sprite webviews (C1 + C2)

**Double input routing (C1).** Bevy's `Mesh2d` insertion makes sprite webviews match the
mesh-path filters. `setup_observers` (`Added<WebviewSource>`) matches only when the
`WebviewSource` is added after Bevy has inserted `Mesh2d`, but `on_mouse_wheel` matches every
sprite webview from its second frame. With a `Camera3d` in the scene, `WebviewPointer`
raycasts against the sprite's AABB and sends CEF a second, wrongly mapped event.
`MeshWebviewFilter` excludes `Sprite` everywhere.

**Rebind (C2).**

- Symptom without the fix: the sprite material is first prepared against the initial image
  (a 1×1 `Image::default()` on the CPU path, the placeholder on macOS). When the image is
  reallocated — first paint, every resize — `GpuImage::prepare_asset` creates a new texture
  (`bevy_render-0.20.0/src/texture/gpu_image.rs:70-164`), but nothing re-prepares the
  material, so the sprite shows a stale or black texture from the first frame.
- `mark_sprite_webview_images_changed` (`src/webview/gpu_surface.rs:773`) is replaced by a
  system that touches the entity's `MeshMaterial2d<SpriteMeshMaterial>` asset with the
  existing `touch_asset` helper, on the same `WebviewSurfaceRebind` frames.
  - Bevy assigns/reassigns the sprite material in a private `PostUpdate` system, so the touch
    cannot be ordered after it. This is covered twice: a resize changes `custom_size`, which
    is part of the material cache key, so a fresh material is created and prepared from
    scratch; and the existing 2-frame rebind echo (`REBIND_FRAMES = 2`) touches the newly
    assigned material on the echo frame.
  - Touching a cached, shared `SpriteMeshMaterial` is safe: the cache key includes the image
    id (`sprite_mesh/mod.rs:82-164`), so only sprites showing the same image share it.
- macOS: `inject_webview_gpu_images` gains
  `.before(prepare_erased_assets::<MeshMaterial2d<SpriteMeshMaterial>>)`.
- Windows/Linux: the sprite `render` system (`src/webview/webview_sprite.rs`) touches the
  entity's `MeshMaterial2d<SpriteMeshMaterial>` on every paint, mirroring
  `render_standard_materials` and the UI `render`. If the material is not assigned yet, there
  is nothing to touch; the material is then prepared fresh when Bevy assigns it.
- `touch_asset` lives in `src/webview/gpu_surface.rs`, which is `#[cfg(target_os = "macos")]`
  (`src/webview.rs:24-25`). It moves to the always-compiled `src/webview.rs` as a
  `pub(crate)` helper so both paths share it. `SpriteMeshMaterial` has no field bevy_cef
  writes, so the CPU path cannot rely on an incidental `DerefMut` the way the mesh path does.
- Known cost, accepted: during a drag-resize every new `custom_size` creates a new cached
  `SpriteMeshMaterial` (`src/resize/pipeline.rs:60-73`); Bevy evicts unused ones.

### Render graph ordering (C2)

`webview_blit` must record its blit before the camera passes. Under the weak chain this
still holds: `camera_driver` is exclusive (`bevy_core_pipeline-0.20.0/src/schedule.rs:136-139`)
and `RenderContext` carries `Deferred` state (`bevy_render-0.20.0/src/renderer/render_context.rs:232-238`),
and the scheduler keeps weak edges in both cases (`bevy_ecs-0.20.0/src/schedule/schedule.rs:1504-1530`).
The registration gains an explicit `.before(RenderGraphSystems::Render)` and the comment at
`src/webview/gpu_surface.rs:186-191` is rewritten to state that requirement instead of the
old "chained" claim.

### UI materials (no change)

`extract_ui_material_nodes` now re-extracts only changed nodes, but extracted nodes store the
material asset id, and `SetUiMaterialBindGroup` resolves the prepared material at draw time
(`bevy_ui_render-0.20.0/src/ui_material_pipeline.rs:250-272, 329-466`). Touching
`WebviewUiMaterial` still rebinds, and the existing `.before(prepare_assets::<PreparedUiMaterial<WebviewUiMaterial>>)`
edge stays.

## Public API (breaking, 0.14.0)

- Requires Bevy 0.20 and Rust 1.97.1+.
- Custom webview material shaders are WESL and import the helper from its new path:

  ```wgsl
  // 0.13 (.wgsl)
  #import webview::util::{surface_color}
  // 0.14 (.wesl)
  import bevy_cef::webview::util::surface_color;
  ```

  The rest of a user's shader migration (`.wesl` extension, `constants::MATERIAL_BIND_GROUP`,
  Bevy module renames) is Bevy's own 0.20 migration.
- No Rust API of bevy_cef changes beyond what Bevy's own types force (user observers on
  webview entities use Bevy's flat pointer events).

## Error Handling

No new error paths. Shader errors surface only at runtime as Bevy pipeline-compilation
errors in the log; the verification plan runs every shader. If a sprite material is not yet
assigned when a rebind or paint happens, the touch is skipped (`touch_asset` is a no-op for a
missing id), and the material is prepared fresh when Bevy assigns it.

## Verification

Prerequisite: a Rust ≥ 1.97.1 toolchain (`rustup update stable`).

**Static (each commit).** The commands in Requirement 8 and 9, plus
`grep -A1 'name = "cef' Cargo.lock` showing `152.3.0+152.0.6`.

**Automated test (C1).** One pure-ECS regression test, no CEF or GPU, next to the existing
unit tests (e.g. `src/drag.rs`): an entity with `Sprite` + `Mesh2d` + `WebviewSource` does
not match `MeshWebviewFilter`, and one with `Mesh3d` + `WebviewSource` does. It runs in CI.

**macOS hardware (after C2).** Reinstall the debug render process, then run all 18 examples
with `--features debug` and check the log for shader/WESL errors. Focus:

| Example | Checks |
|---|---|
| `simple` | internal standard-material shader, `alpha_discard` |
| `custom_material` | user shader importing `bevy_cef::webview::util` |
| `headless_texture`, `ui_webview` | UI shaders; rebind under retained UI |
| `sprite` | first frame not black; input not doubled; color/alpha; same-Z draw order |
| `resize`, `hidpi` | mesh and sprite rebind after resize |
| `toolbar_drag` | drag path with the new filter |
| `js_emit`, `host_emit`, `brp` | bevy_remote 0.20 |

Also: app activation on launch (`Window::focused`), and an HDR `Camera2d` visual check.

**Windows hardware (after C2).** Rebuild and reinstall the render process from the branch,
then run `simple`, `sprite`, `resize`, `ui_webview`, `custom_material`, `devtool`, `js_emit`,
`brp`. Focus on the CPU-path sprite (first frame, resize, per-paint material touch) and
pointer input.

**Linux.** CI only.

## Deliverables

- C1: `MeshWebviewFilter` alias at four sites + regression test.
- C2: dependency/MSRV changes, compile fixes, five WESL shaders, IOSurface import update,
  sprite rebind fix (including moving `touch_asset` to `src/webview.rs`), render-graph
  ordering comment.
- C3:
  - Workspace version and internal dependency versions → `0.14.0`.
  - README: compatibility row `| 0.20 | 0.14.0 | 152.3.0+152.0.6 |`, MSRV note.
  - CLAUDE.md: compatibility table; replace the nonexistent `WebviewSpriteMaterial` with the
    `Sprite`-based description; render-graph ordering wording; WESL note; MSRV.
  - CHANGELOG: v0.14.0 entry (Bevy 0.20, MSRV 1.97.1, shader import migration guide).

## Out of Scope

- Any CEF version change, including 152.4.0; the JS bridge rewrite needed for CEF ≥ 154
  (`register_extension` removal) and the CEF 156 move.
- Replacing `Sprite` with a bevy_cef-owned `Mesh2d` + `Material2d`.
- Forwarding `PointerPress.count` (double-click) to CEF.
- `docs/website/` refresh.
- Migrating the remaining `objc` 0.2 usage to `objc2`.
